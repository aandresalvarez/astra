# ASTRA Dev baseline · November 2, 2026

The full application completed three fresh processes per condition, each with
one warm-up and three measured cycles, returning to idle for 10 seconds after
each cycle. All six processes preserved exactly **23 workspaces, 2,195 tasks,
115,977 events, 5,868 runs and 30,110 artifact records**. Source data were wholly
synthetic. The long thread had 30,000 events; the saved workspace had 425 tasks,
15,259 events and 1,236 runs. Each save's exact instruction text was verified in
the workspace mirror (approximately 17.4 MB, not task-file bodies).

The source app reported commit `b7908367b8fe` (common main
`b7908367b8fe09f1bc4381d1f0192d8e828a8636`), version **0.1.30 (10030)**,
schema **21**, packaged and linked channel **dev**, App Intents disabled, build
date `2026-11-02T23:43:31Z`. An existing bundle was copied and ad-hoc re-signed;
no app source was changed. Its source executable SHA-256 matched before and
after both conditions. Both previously running user applications stayed in place.

The host was **Mac15,7, 36 GiB RAM, macOS 26.6.2, Apple Swift 6.4, AC power**.
It was shared and active, with other ASTRA processes running. Initial 1/5/15-minute
load averages were **10.58/11.98/15.80** for the file case and
**9.47/11.03/12.88** for the empty-folder case. Conditions ran sequentially,
not counterbalanced, with no CPU isolation or disk-cache purge. Host load,
per-run load averages, build/source hashes and local-time sample windows are in
the JSON summaries. Timings are informational, not CI limits.

## Metadata correction and readiness qualification · November 3

The full and no-initial-files captures used **5,376-byte UTF-8 goals**: 336
repetitions of the 16-byte string `Synthetic goal. `. The old recorder labeled
them 5,040 bytes. The two JSON summaries now correct that field and include a
`metadata_corrections` audit entry with the captured value, original summary
commit/SHA-256 and persisted-goal evidence. Replacing the field with its recorded
value and removing that audit entry reconstructs each original summary exactly.
The sidebar controls really used distinct 5,040-byte goals and are unchanged.
No goal content, workload, timing, footprint, allocation or count measurement
has been changed or remeasured for this correction.

The original AX controller also failed to decode errors in individual returned
attributes. Such an error could falsely establish absence, including initial
state checks. The capture did not retain per-attribute error statuses, so those
historical readiness checks cannot be certified with the corrected parser.
All raw timing values remain historical observations; rerun the corrected
controller before treating them as validated latency comparisons.

## Physical footprint and live allocation evidence

MiB means 1,048,576 bytes. Peak is the kernel-reported lifetime physical
footprint; final idle is measured after all cycles and Leaks collection. Heap
change compares live malloc storage from `heap --noContent -s` after warm-up
with final idle. These counters measure different things and must not be added.

| Condition / fresh process | Launch (s) | Warm idle (MiB) | Peak (MiB) | Final idle (MiB) | Live malloc change (MiB) | Leaks-reported bytes |
|---|---:|---:|---:|---:|---:|---:|
| 48,414 initial files / 1 | 8.78 | 307.7 | 333.5 | 207.2 | +2.33 | 14,336 |
| 48,414 initial files / 2 | 8.35 | 295.2 | 326.2 | 173.4 | +1.78 | 14,400 |
| 48,414 initial files / 3 | 8.86 | 292.2 | 325.0 | 211.6 | +3.40 | 14,272 |
| No initial files / 1 | 8.13 | 249.0 | 361.3 | 186.2 | +1.98 | 14,368 |
| No initial files / 2 | 7.97 | 257.1 | 319.5 | 186.4 | +2.10 | 14,016 |
| No initial files / 3 | 7.81 | 259.1 | 293.4 | 194.4 | +1.64 | 14,208 |

Initial file bodies totaled **2,230,871,040 logical bytes (2.08 GiB)** but
**198,299,648 allocated bytes (189.1 MiB)** because they were sparse synthetic
text files. The control retained the same database and relative artifact paths,
with no initial task-folder files. ASTRA generated four task-state files and two
workspace files in every run: final task-folder counts were 48,418 and 4,
respectively. This is file presence/list pressure, not realistic document content.

Peak ranges overlap across the conditions. These small sequential samples do
not establish a file-volume memory effect. Idle physical footprint fell in each
process, while live malloc storage increased by 1.6–3.4 MiB. Leaks reported
14,016–14,400 bytes in 280–288 allocations across the six processes. This is
not a leak-free verdict or a reference/ownership analysis. Final heap summaries
displayed 2,195 `AgentTask` objects and one `ModelContext`; individual class sizes
exclude their backing graphs. Raw heap and vmmap summaries remain local.

## External readiness timings

These are **input-to-accessibility-ready upper bounds**, not pixel presentation
or handler-only timings. Observation cost sometimes dominates: the median final
query for the short thread itself took about 6.25 seconds in the file case.
Do not interpret that row as a measurement of user-perceived switching delay.
Queries were batched, retried on overall API failures/incomplete traversals and
scoped for sidebar rows, subject to the per-attribute limitation described above.
Native mouse clicks were used for folders, tasks and Save; menu setup and the
Files toolbar used explicitly labeled accessibility actions.

and its fields. No rendering, history, run/artifact rows or task-folder files
were included. Goals were distinct synthetic 5,040-byte strings.

Task-row volume had a much larger cost than workspace count in this model-fetch

## Reproduce and inspect

See the [benchmark guide](../dev-scale-benchmark.md) for tool compilation,
fixture generation, isolation checks and all options. The captured commands used
an existing matching development bundle and its read-only model build directory:

```sh
python3 script/benchmarks/dev_scale_benchmark.py \
  --app "$BASELINE_DEV_APP" --build-dir "$BASELINE_MODEL_BUILD_DIR" \
  --tools "$PWD/.artifacts/dev-scale" --fixture "$PWD/.artifacts/dev-scale/full" \
  --output "$PWD/.artifacts/dev-scale-full" \
  --runs 3 --cycles 3 --idle-seconds 10

python3 script/benchmarks/dev_scale_benchmark.py \
  --app "$BASELINE_DEV_APP" --build-dir "$BASELINE_MODEL_BUILD_DIR" \
  --tools "$PWD/.artifacts/dev-scale" --fixture "$PWD/.artifacts/dev-scale/full" \
  --omit-task-files --output "$PWD/.artifacts/dev-scale-no-files" \
  --runs 3 --cycles 3 --idle-seconds 10
```

- [Same database without initial files](2026-11-02-b7908367-no-files.json)

Failed controller preparation attempts were excluded. This fixed two-thread
workload, serial successful saves and short observation window do not model
four days of activity, thousands of unique task switches, real payload/content
distributions, Git/SSH/provider activity, or queued credential-cleanup work.
All full-profile goals repeat the same synthetic text; the sidebar controls use
distinct goals. Every task is completed but review-eligible, so the 425-task
folder is intentionally a heavy drawer case. The six full-app runs did not
reproduce the older application's reported 1,336 MiB footprint, and do not
identify its cause or establish that another revision would fix it.
